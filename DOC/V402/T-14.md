## 0. 结论

- **差异不在 FFmpeg 版本号**：主线与 DEMO 的 libavformat/libavcodec/libavutil 均为 62.3.100 / 62.11.100 / 60.8.100。
- **差异在四层**：① 构建配方（DEMO 加 `--enable-libsmb2`、工具链/SDK 不同）；② 0020 的读模型（本地自持）；③ HAR 打包/版本（2.0.11 vs 2.0.13、arm64 only、多 `libsmb2.so.1`）；④ 主项目 A 路径的 ArkTS 集成（DEMO 代码不能直接搬）。
- **最小合并路径**：以 0020 为唯一 FFmpeg 补丁 → 重编 arm64 → 重链 `libijkplayer`/`libijksdl` → 本地化 HAR → 与 B 路径去重 libsmb2 → V401 回归；主项目 A 路径另按 ports/flows 重写。

## 6. ABI 与版本兼容性

- **版本号**：两端 libavformat 62.3.100、libavcodec 62.11.100、libavutil 60.8.100；符号版本分别为 `LIBAVFORMAT_62`、`LIBAVCODEC_62`、`LIBAVUTIL_60`，两端一致。
- **NAPI/FFmpeg 符号**：
  - 两端 `libavutil.so` 均导出 `av_application_open/close/closep/alloc/on_io_control/on_io_traffic/on_async_read_speed/will_http_open/did_http_open/will_http_seek/did_http_seek/on_tcp_will_open/on_tcp_did_open/did_io_tcp_read`，版本标签 `@@LIBAVUTIL_60`。
  - 两端 `libijkplayer.so` 均导入 `av_application_open/closep/on_io_control@LIBAVUTIL_60`；两端 `libavformat.so` 均导出 `ff_check_interrupt@@LIBAVFORMAT_62`（IJK 唯一私有导入）。
  - `libijkplayer.so` UND 符号数 324/324；`libijksdl.so` 129/129；`libijkplayer_napi.so` 导出 mangled 名集合相同（地址不同）；`libavformat/libavcodec/libavutil` 的 defined 名集合也完全一致（163/164/644）。
- **判断**：**不存在版本号导致的 ABI 硬冲突**；“libijkplayer.so 必须同源重编”应理解为**交付/工程要求**（同 build、同 flags、同 HAR、可回归），不是版本不同导致的必然不兼容。若要混载主线 `libijkplayer` + DEMO FFmpeg，符号面大概率能解析，但属未验证组合，不建议作为交付形态。
- **唯一私有符号** `ff_check_interrupt` 两端都在；`av_application_*` 函数体大小有差异（如 `will_http_open` 184 vs 140 B），属不同编译选项，功能需回归，不是缺失。

## 8. 合并路线建议

### 8.1 最小路径（必须做）

1. **FFmpeg**：以 `0020` 为唯一补丁（不要 0019+0020 叠加），保留 `--enable-ohcodec`、`--enable-openssl`、`--enable-shared`、`--disable-static`；加 `--enable-libsmb2`；对齐 `--disable-librtmp`；先 arm64，x86_64 按需。
2. **IJK/HAR**：同源重链 `libijkplayer`/`libijksdl`，加 `libsmb2.so.1` 依赖；本地化 HAR，保持 ETS/NAPI 不变；包版本/`oh-package`/`module.json` 对齐主项目。
3. **libsmb2 去重**：只保留一份 `libsmb2.so.1`（B 路径 `ohos_libsmb` 或 IJK HAR 二选一），确认 `libsmbsession.so` 与 `libavformat.so` 都解析到同一文件。
4. **主项目 A 路径**：按 `kernel/ports` + `flows/playback` + `PlaybackCommandCenter` 重写行为，不搬 DEMO `Index.ets`；latest-wins 放播放层（Q9）。
5. **V401 回归**：SURFACE、双槽预加载、4K60 狂拖、稳态 CPU 14% 四项同条件复测。

### 8.2 可延后

- x86_64/模拟器 ABI（若主线不再需要）。
- 0020 的协议层进一步调参（环大小/预取块）。
- SMB3 seal、HTTPS 真实点播、断网重连。

### 8.3 与 B 路径共存

- 同 SONAME、同 4.0.0、同 stripped SHA；**没有版本冲突**，但有两个模块各打包一份的风险。合并后只留一份，避免加载到不同副本。
- `libsmbsession.so`（B）与 `libavformat.so`（A）可同时 NEEDED 同一 `libsmb2.so.1`；双 context 并发（预加载 + 播放）未验证，需专门用例。

### 8.4 与 V401 基线

- `--enable-ohcodec` 保留、IJK C++ 源码 0 改动 → SURFACE 硬解路径设计上不变；风险在 **`libijksdl`/libavcodec 重建**与 `libijksdl` 体积差异。
- 双槽预加载属 ArkTS 层（`IjkPreloadCtl`/`SmbPlaySlots`），换 HAR 不改其代码；但 A 路径新增 `smb://` 与 B 路径代理共用 libsmb2，需测“预加载 + 播放同时读”。
- 合并后必须复测 V401 的 SURFACE、双槽、4K60 4 ms 狂拖、稳态 CPU；不能只看 CPU 15.2%。

## 9. V402-050 裁决回执：版本方向、CI 约束、HAR 适配与 0020 审查前置

> 裁决输入：T-14-EXCERPT `16c69a0`。本节只登记，不改代码；§9.1/§9.2 为可判定结论，§9.3/§9.4 为独立子项。

### 9.1 §B-7 方向（一句话）

**主项目升级/切换到本地构建的 2.0.13 HAR，不是把 DEMO 降回 2.0.11**；“2.0.13→2.0.11 线”仅指版本/元数据/锁文件向主线 2.0.11 依赖线做**兼容适配**，功能基线仍是 2.0.13 + 0020。

依据：

- 0020 的 libsmb2 / 预取环只存在于 2.0.13 的本地 HAR 构建：2.0.11（ohpm registry）是 14 库、无 `libsmb2.so.1`；2.0.13 是 15 库（§5）。
- 主线 `libs/ohos_ijkplayer/oh-package.json5` 与 `entry/oh-package-lock.json5` 当前 pin `@ohos/ijkplayer@2.0.11`（registry resolved + integrity）；采用 2.0.13 必须把依赖改成本地 HAR 并更新 lock（见 §9.3）。
- 降回 2.0.11 会丢掉 A 路径所需的 libsmb2/预取环，等于放弃合并目标。

### 9.2 主线 CI 是否强制 x86_64 双架构（一句话）

**否，首批 arm64 only 成立。**

依据：

- 仓库当前**没有启用的构建 CI**：`.github/workflows.disabled/governance.yml` 只跑 `scripts/repo-guard.mjs` 与 `tests/unit/run.mjs`，不构建 HAP、不检查 ABI。
- `entry/build-profile.json5` 的 `nativeLib.filter.excludes` 明确排除 `**/x86_64/**`；`libs/ohos_libsmb/build-profile.json5` 的 `abiFilters` 只有 `arm64-v8a`。
- 条件：若未来 CI 新增 HAP 构建且要求双架构，本项需重开另议。
