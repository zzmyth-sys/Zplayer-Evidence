## 1. Q1：恢复动作与用户 seek 的关系

### 1.1 事实底座（只引用）
- 双 seek 可达：retry 传入的 backend 是调用时求值的引用（`PlaybackOpsCtl.ets:159` + `PlayerOps.ets:19-25`），prepare 期间可换实例（`PlayerAssembly.ets:211,257,521-522`），Gate 每实例一份（`IjkPlayerBackend.ets:91`）。
- 续播位直接写 backend（`PlayerOps.ets:13-14`），不经 CC 事件。
- CC 下游固定为 `CommandRunner.ets:76-78` → `BackendPlaybackExecutor.ets:44-46`；准入只看 Store 状态与 `releasing`（`CommandAdmissionCtl.ets:9-28`）。

### 1.2 选项
| 选项 | 含义 | 必要性/代价 |
|---|---|---|
| A | 恢复动作全部纳入 CC（retry/续播变成 CC 命令族） | 字面满足「唯一门禁」；但 retry = prepare + seek 的复合长操作，会占用 CC 单执行槽或需要新的抢占语义；且 retry 当前复用句柄、不铸新 epoch（`PlaybackOpsCtl.ets:158-161`），纳入后必须重新定义 epoch/identity 语义 |
| B | CC 继续只管用户命令；新增“生命周期 owner”层，独占当前 backend 句柄、独占 Gate、独占票据；CC 与恢复动作都只能经 owner 取句柄/提交 seek | 需澄清宪法口径；结构性消灭“旧实例引用”与“双 Gate”；不改变 CC 的命令排序/epoch 职责 |

### 1.3 推荐：B，并附宪法解释
- **「门禁唯一」= 唯一仲裁点，不必然是唯一调用入口。** CC 仍是唯一对“用户/流程命令”做准入、排序、epoch 铸发的地方；owner 是唯一对“seek 资源（实例句柄 + 闸门 + 票据）”做仲裁的地方。恢复动作不是命令，是生命周期动作，因此走 owner 而不是 CC，但**必须走同一张票据表**，不得另建闸门。
- 若裁定「所有 seek 入口必须物理上经过 CC」（字面口径），则退 A；此时 owner 仍然必要（否则实例漂移无解），只是 owner 降为 CC 的执行后端。**这是口径之争，不是实现之争，必须先裁。**
- 理由：A 会把 prepare 生命周期塞进命令槽，直接触碰 epoch/identity 语义（`PlaybackCommandCenter.ets:80-104`），回归面大于收益；B 只收敛资源所有权，保留 CC 现有语义。

### 1.4 影响面（B）
- 句柄所有权：`PlayerAssembly`（唯一 `setBackend` 点收归 owner）。
- 命令执行：`BackendPlaybackExecutor` 改为经 owner 取当前句柄（消除调用时快照）。
- 恢复路径：`PlaybackOpsCtl.retry` / `PlayerOps.applyResume|retryPlayback` 改为向 owner 提交（不得直取 `deps.backend()`）。
- 仲裁策略（设计级要求，不写实现）：用户 seek 优先于恢复 seek；恢复 seek 必须可被取代/幂等；实例切换后旧票据一律作废；owner 必须能回答“当前是否有未完成 seek”。
- 测试：双 seek 场景从“不可测”变为可注入（旧实例引用、换实例窗口）。

## 2. Q2：唯一真源与在飞门控

### 2.1 选项
| 选项 | 内容 | 判定 |
|---|---|---|
| T1 | 沿用现状：`getCurrentPosition` 直接发布为 Store 权威位置 | 否：T-18 §12 已证无任何 seek/busy 抑制（`Ijk:420-426,:435`），T-19 §3.1 的 11s 假 stall 即由此产生 |
| T2 | 原生读数 + seek 票据门控：区分「采样值」与「已确认真值」 | **推荐** |
| T3 | 用 vdec PTS/渲染帧位置做真值 | 否：应用内无 PTS 通路（T-18 §1 P8 未定位），且 T-19 §4 的 PTS 只存在于设备日志，不能进 Store |

### 2.2 推荐：T2 —— 真值的定义
- **真源 = “已确认的控制位置”**，不是“画面实际落点”。T-19 §4:100-101 证明 `done pos` 可等于目标值而 vdec PTS 偏差 4–7 s，因此必须显式声明：T-20 只保证控制真源自洽，**不承诺落点精度**；落点验证（E2）独立立项。
- **门控条件（依赖的状态位，设计级）**：
  1. 票据：当前 seek 票据 id + 阶段（Idle / InFlight / AwaitingAck / Settled）；
  2. 实例身份：当前 backend 实例 id（或等价的 epoch/代数）；
  3. 原生状态：Prepared / Playing / Paused / Completed（不可在 Idle/Initialized 采信位置）；
  4. 最后确认位置 + 其确认时刻。
- **在飞期间返回什么**：返回 **最后确认位置**，并携带 `stale`（不可作为“已落位”证据）。**不得返回目标值**，也不得把 500ms 轮询读数当成新真值。
- **Gate 在飞时如何处理**：轮询只产生“采样”，不推进权威位置；只有票据被确认（原生 seek 完成）后，该时刻的读数才可提交为真值。票据超时/作废时，位置保持最后确认值，直到出现“无票据下的推进”才重新确认。
- **实例切换/epoch 变化**：所有在飞票据作废，位置进入 Unknown（不是 0），等新实例 Prepared + 首个确认读数。
- **幂等要求**：迟到的确认（旧票据/旧实例）必须被丢弃，不得回写。

### 2.3 影响面（T2）
- backend 位置发布：`Ijk:293`/`:423` 的读数语义从“真值”降为“采样”（不改原生调用，改上层采信规则）。
- Store：位置写入多一条“确认”判据（`PlaybackReducer:142-150` 的入口语义变化）。
- 看门狗：`PlaybackEngine.progress()`（`:83-95`）的 `posMs`/`seeking` 语义改为“已确认位置 + 票据在飞”，供电给 Freeze。
- UI：`seekPreviewMs` 保持现状（展示层），但**不允许再被当作落位证据**；`displayMs()` 的多源读取（`GestureLayer:174`、`ShortVideoSwiper:252-253`）需在设计上标注为“展示基点”，不得进入真值链。
- 风险：若只做门控而不给 Freeze 补“seek 边界信号”，会架空 `edeadea`（见 §4）。

## 3. Q3：合并窗 / 冻结窗 / 沉降三者的参数关系

### 3.1 选项
| 选项 | 内容 | 判定 |
|---|---|---|
| P1 | 保持 8s / 8s / 12s，不加关系约束 | 否：三值等长是巧合；8s 合并窗与 8s 冻结窗在 seekDone 丢失时会“同拍竞速”，无法证明先合并后判冻 |
| P2 | 单纯放大冻结窗（如 21s） | 否：把 P0 的检出时延拉到 20s 以上，且不解决“无票据时无法区分 seek 与停滞” |
| P3 | 用状态门控取代大小排序，并固化可证明关系 | **推荐** |

### 3.2 推荐：P3
符号：`T_s` = 冻结采样 1s（`PlayStallWatchdog.ets:24,240-245`）；`G` = 合并/看门狗上限 8s（`SeekGate.ets:12-14,102`）；`S` = 沉降上限 12s（`ProgressFreeze.ets:8,105`）；`F` = 冻结窗 8s（`ProgressFreeze.ets:5`）。

三条关系（替代“谁比谁大”的直觉）：
- **R1（门控优先）**：冻结计时只在「无未完成票据 且 不在沉降」时推进。满足 R1 后，`F` 与 `G` **不需要**大小排序；`F=8s` 的含义变成“无 seek 情况下的 8s 真停滞”。
- **R2（沉降必须晚于合并）**：`S ≥ G + 2·T_s + margin`。现值 12 ≥ 8+2+1=11 ✓，说明 12/8 这一对是可辩护的；`margin` 吸收 1s 采样抖动与 Gate 的轮询时间源差异（`SeekGate.ets:6` 事件/轮询驱动 vs 1s 墙钟）。
- **R3（冻结窗下限）**：`F > 2·T_s`，否则单次采样噪声即可判冻；8s ✓。
- **反证关系（若拒绝 R1）**：必须 `F ≥ G + S + 2·T_s ≈ 22s`，否则无法排除“seek 在飞被当成停滞”。这就是 P2 的代价，也说明**8/8/12 在当前代码里不可证明**。

### 3.3 影响面（P3）
- 常数不再独立调参：任一参数变更必须复核 R1–R3；`S`/`G` 改动需同步测试。
- 冻结只在 HLS 生效的现状（`PlayStallWatchdog.ets:263-267`）保持不变；SMB 不进冻结判定。
- 2b 需观测：加门控后 `HLS_STALL_FREEZE` 是否仍可能误报、以及真实传输停滞是否仍能在可接受时延内检出（T-19 §6 的 0/7 复现说明现有阈值尚未被证明）。
