## 2. B 侧链路取证与 CPU 口径（**重要更正**）

### 2.1 结论先行

1. **本轮不存在有效的 B（SMB 代理）运行**。被标为 "B-SMB" 的那段（00:31:10–00:33:57）实际是 HLS。
2. 因此 **`12.75%` 不是 B 侧数据，作废**；它应归入 A（HLS 1080p60 转码流）口径。
3. `12.75%` vs 历史 `~160%` **不是口径错误，是链路不同**（HLS 1080p 转码 vs SMB 代理原始 4K）。

### 2.2 为什么那段不是 B

SFF 由 `run-service.cmd` 的 `:run` 循环托管（`uvicorn exited ... restart in 5s`），本轮"杀 SFF"只造成 **约 5 s** 中断，随后自动拉起：

```text
[Tue 10/27/2026  0:26:16.67] uvicorn exited rc=-1, restart in 5s
[Tue 10/27/2026  0:26:21.73] uvicorn starting
[Tue 10/27/2026  0:28:54.51] uvicorn exited rc=-1, restart in 5s
[Tue 10/27/2026  0:28:59.60] uvicorn starting
```

且 00:31 起播后，`/health` 在 00:34:25 仍返回一个 **active=1 的 HLS 会话**（`id=c14549f8c8df, method=transcode, segments=92`），该会话只能由 00:31 那次起播创建 → 证明 00:31 走的是 SFF HLS。

**缺口**：本轮未能在设备缓冲区内留下该次 `SmbHttpProxy: listening` 行（hilog 缓冲约 1 min 即被系统噪声冲掉），故"B 侧"没有任何设备侧直接证据。**不补造。**

### 2.3 CPU 口径逐项对比

本轮采样口径（与基线文档同）：`top -b -n 1 -p <pid> -o PID,%CPU,RES`，6 次 × 30 s 取中位；该 `top` 表头同屏打印 `900%cpu ... 800%idle`，即**单核百分比、进程内各线程求和、可 >100%**。

| 项 | 基线 `DOC/PERFORMANCE-BASELINE.md` §2/§7 | 本轮实测 | 判定 |
|---|---|---|---|
| SFF HLS 1080p 60（转码流） | App CPU **12.4%**（Codec CPU 36.3%） | **12.75% / 14.2%**（两组 6×30 s 中位） | 同档，链路一致 |
| SFF 2.5K HEVC 60 | App CPU **14.0%**（Codec CPU 35.5%） | — | — |
| SMB 自建代理（原始 4K 2160×3840@60） | App CPU **~160%**（Codec CPU 22.5%，"代理拷贝税≈3.7× CPU"） | 本轮**无**该链路数据 | 缺测 |
| SMB 落盘（本地 4K） | App CPU 12.2%（Codec CPU 26.2%） | — | — |

差异来源拆解：

- **分辨率/码率**：基线 160% 的输入是原始 4K 2160×3840@60（37 Mbps）；本轮 HLS 由服务端按 `ZP_MAX_WIDTH/HEIGHT=1920×1080` 转码（`encoder=hevc_nvenc`），设备只解 1080p60。
- **链路税**：SMB 代理多一层"读→本地 HTTP→ijk"的拷贝（基线记为 ≈3.7× CPU），HLS 无此税。
- **口径不是差异来源**：两者都是同一 `top` 进程 CPU、6×30 s 中位；本轮只是**没有采到** Codec CPU 列（media codec 独立进程），这一列不能与历史表直接比。
- **解码方式**：两条路都是 `VideoCodecMode.SURFACE` + OHCodec 硬件解码（hilog 出现 `[h.vdec]{Start} success`），**不是软解**；本轮 12–14% 属硬件解码 1080p60 的正常量级。

## 3. P0 缺陷登记：播放中传输看门狗（P0-1-WD）未实现

**缺陷 ID**：`P0-1-WD`（沿用已登记名，本轮首次给出真机复现证据）
**级别**：P0（主力链路 S 的用户可见卡死，且不可自愈）
**状态**：已登记，未修复（本轮不改业务代码）

| 00:42:16 | 进程被外来安装杀掉（与本缺陷无关） | AMS `UpgradeApp` |

- 无 `DOWNGRADE_OK/FAIL`、无 `SmbHttpProxy listening`、无错误遮罩（OCR 全屏文本无"错误/重试/不支持"），无 Fatal、无 cppcrash/jscrash。
- 另一次操作：00:27:53 按播放 → 00:27:54.124 音频 `Start` → 00:27:54.285 音频 `Pause`（**161 ms**）后再无动作，同样不降级。

对照（同仓 `T-01-REALDEVICE.md`，10-26 22:57）：当 ijk **显式报错** `what=-10000` 时，降级链完整走通（`STREAM_FAIL → HLS_STREAM_FAIL → LEASE_CREATE → SmbHttpProxy listening → DOWNGRADE_OK`，约 350 ms）。

**缺陷定义**：当前只有"开播前/开播期"的失败降级；**播放中**若传输层不报错而静默停滞（短时断流、服务端重启、分片超时后恢复），无看门狗判定停滞、无重试、无降级 → 画面永久冻结且无用户提示。

**影响面**：主力链路 S。服务端计划内重启（5 s 级）即可造成用户侧永久卡死，且退出重进才恢复。

**T-01 处置**：**不得关闭**。验收范围扩为两段：
1. 开播前降级（现状已通，`T-01-REALDEVICE.md` 已证）；
2. **播放中降级（缺 P0-1-WD，未达标）**。

**取证缺口（须补）**：本轮冻结窗口的 App 侧 hilog 已被缓冲区覆盖，且 `PROBE_LOGS=false` 无 `state=Playing`/stall 行；需要一次开启探针的测试构建 + 立即落盘（`hilog -x -P <pid>` 持续写文件）复现，才能把"冻结时刻"与"停滞判定缺失"钉成直接证据。
