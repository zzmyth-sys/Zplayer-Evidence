## 1 范围与前置

- **只测**：`HLS 失败/停滞 → HlsDegradeCtl.fail → SourceDowngradeCtl → SMB 代理 → 新源 Prepared`。
- **不测**：DEMO/A 路径、12G、快速切换、B 路径 cppcrash/UAF、SFF 4K 直通、seek 性能。
- **前置控制组**（任一不成立则停测）：
  1. SFF `/health` 200，`/probe`、`/stream/start`、`/hls/.../index.m3u8` 正常；同一素材正常 HLS 起播到 Playing。
  2. SMB 共享可达，主项目同一素材正常 SMB 代理起播到 Playing（证明降级目标本身可用）。
  3. 主项目 HAP 已安装（非 Demo），前台、屏幕常亮、无其它播放器；日志缓冲已清空。
  4. 同一素材、同一起播点、同一设备；每轮冷启动或 `force-stop`，避免上一轮残留。

## 2 触发路径与判定条件

> 所有 T1/T2 都要求在 **prepare 返回 `Ok` 之后、首帧 `VIDEO_RENDERING_START` 之前**注入；若已出首帧，该轮作废重跑。

### T1 传输失败（三条子路径）

| 子路径 | 注入方法（不改代码） | 客户端判定 | 服务端判定 | 备注 |
|---|---|---|---|---|
| **T1a 504** | prepare 返回 Ok 后、首帧前，挂起 SFF 的 ffmpeg 子进程/使段生成超过服务端 5s 预算；`app/hls.py` 的 `wait_for` 超时返回 504 | `IjkPlayerBackend.onError`（`:304-327`）；URL 为 HLS 且 code 非解码类 → `STREAM_FAIL stage=hls-segment`；不置 Error、不发 Fatal | `/hls/{id}/seg-N.ts` 返回 **HTTP 504**；服务端日志确认 | 504 以服务端响应为准；客户端日志不要求出现“504”字样；无法产出真实 504 时记“504 未取得”，不得用断连冒充 |
| **T1b 断连** | prepare 返回 Ok 后、首帧前，kill SFF 进程或封 8612 端口；TCP RST/refused/timeout | 同上：`ijk error` + `STREAM_FAIL`；无 Fatal | 无 HTTP 响应/连接失败，非 504 | 与 504 分开记录，不能互相替代 |
| **T1c 无帧** | onPrepared 已触发、视频看门狗已启动（:278）后，首帧前挂起 SFF（进程存活但不供数据），或让 ffmpeg 不产出视频帧 | `IjkPlayerBackend` 视频看门狗 **3s**（`VIDEO_WATCHDOG_MS=3000`，`:34`；`:438-473`）到点 `fps=0` → `STREAM_FAIL msg=ijk: no video frames` | 请求挂起/无段数据 | 必须在 8s 停滞前触发；若 onPrepared 未触发或 8s 先到，本轮记为 T2，不算 T1c |

- **解码失败排除**：`isDecodeFailureCode` 命中（如 `-1094995529`、`-38`、`-541478725`、`5400106`）时不走降级，仍 Fatal；这类样本不得算 T1 通过。

### T2 停滞看门狗

- **判定**：prepare 返回 `Ok` 且 ticket 仍当前后 arm（`PlayerInitLayer.ets:149`）；`HLS_STALL_HINT_MS=8000`（`PlayStallWatchdog.ets:19`）。
- **8s 起算点**：从 **arm 时刻** 起算，不是用户点击、也不是请求发起；若 prepare 用了 4s，最坏约 12s 才触发。
- **触发条件**：arm 后 8s，Store 状态仍为 `Prepared`/`Initialized`（映射为 `Prepared`），且非 `Playing/Paused/Error/Released`、非 Ended。
- **注入**：prepare 返回 Ok 后、首帧前挂起 SFF（不杀进程，避免 onError 抢先），让无数据但连接不报错；观察 `HLS_STALL state=Prepared/Idle reqId=...`。
- **不算 T2**：8s 内已 Playing、已 Error/Released、已 Ended，或先由 T1 onError/无帧触发。

## 3 降级成功判据

### 功能成功（必须全部满足）

- 关键日志 **恰好一次** `DOWNGRADE_OK trigger=...`；无 `DOWNGRADE_FAIL`；无 Fatal。
- 新源进入 `Prepared` 并到 `Playing`；`listening <loopback>:<port>` 出现；活动 URL 变为 `http://<loopback>:<port>/video.mp4`（SMB 代理）。
- 播放位置继续前进（`pos` 单调）；音频不断流（主观+日志）。
- 时延（暂定，待裁）：触发到 `DOWNGRADE_OK` ≤ `OPEN_TOTAL_MS`（5000）+ 1000ms 调度；T2 从 arm 到新 Playing ≤ 8s + 5s + 1s。

### 画面与提示

- **不黑屏**：触发后 3s/5s 采样，视频区不得命中 `mean<5 且 std<3`；0–1.5s 切换空窗若黑屏，记录空窗时长，**>1.5s 即 fail**；0.5s/1s 采样只用于测空窗长度，不单独判 fail。
- **T1 提示**：`onError`/无帧分支不发 `ErrorRaised`，UI 应 **完全无错误遮罩/无错误文案**（静默）。
- **T2 提示**：`PlayStallWatchdog` 会发 `ErrorRaised -4 Recoverable 'HLS 拉流超时'`（`:161-168`）；`EventMap` 对 `ErrorRaised` 一律发 `EV_UI_ERROR`，`PlayerPage` 写入 `errorMsg`，`ErrorOverlay` 显示错误文案+“重试”，直到新源 `Playing` 才清（`PlayerPage.ets:157-162/190-191`）。**V402-035 已裁决：T2 短暂遮罩不算弹错**；T1 仍要求 UI 静默；文案“HLS 拉流超时”待改，另立单。
- **播放继续**：新源 Playing 即可；**不保证续播到原位置**：`SourceDowngradeCtl` 走 `prepareDetailed`，`startPositionMs` 固定 `-1` 且未被消费，可能从 0 起播；执行时记录首帧位置，若要求“从当前点续播”，另立缺陷单，不在本轮修。

## 4 降级只发生一次的判据

- 同一 `uri#gen`（v1）或 `uri#gen#attempt`（v2）只允许 **一次** `DOWNGRADE_OK`；第二次 `DOWNGRADE_OK` 即 fail。
- `HlsDegradeCtl.inFlight` 吸收并发重入；`SourceDowngradeCtl.tried` 吸收同键重复；`prepareChain` 对同 uri 串行。
- 允许出现的日志：`DOWNGRADE_SKIP reason=inflight/stale-*`；不允许第二次 `DOWNGRADE_OK`、第二次 `listening`（同键）、第二次 SMB `Prepared`（同键）。
- T1 与 T2 同时命中（如 504 后 8s 又停滞）：预期只降一次，第二个触发被 `inFlight`/`tried` 吸收；若出现两次降级即 fail。
- 成功播放后不得再出现 `HLS_STREAM_FAIL`→`DOWNGRADE_OK` 循环；SMB 侧自身失败按 §5，不算 HLS 循环降级。

## 5 降级失败时的兜底

- **SMB prepare 返回 `Failed`**：
  - `SourceDowngradeCtl` 发 `DOWNGRADE_FAIL` + `PlaybackError -4 Recoverable 'hls downgrade failed'`；该 Recoverable 不经 `EventMap` 上屏。
  - `HlsDegradeCtl` 在 `isCurrent` 时发 **一次** `ErrorRaised` Fatal（原始 code/message）→ `ErrorOverlay` 显示原文 + “重试”；播放停止；不再自动重试。
- **SMB prepare 抛异常（F7）**：异常上抛，`PlayerBootstrapper` 只 `catch` 记日志（`:257-260`）；**不保证 Fatal/遮罩**，可能黑屏或冻结。V402-035 裁决：无 UI 不接受，另立 `P0-1-F7`，P0-1 关闭前必须补；本轮若触发，记为预期内缺口，不算测试失败。
- **用户可见文本**：原始 IJK 文本 `ijk:<what>/<extra>` 或 `HLS 拉流超时`；若 SMB 失败，仍显示原始触发原因，不显示“SMB 失败”以外的编造文案。
- **不循环**：失败后不得自动再次尝试 HLS→SMB；用户点“重试”才发起新请求。

## 10 降级链与 CommandCenter 的关系

### 10.1 调用事实（以当前代码为准）

- 降级入口：`HlsDegradeCtl.fail` → `SourceDowngradeCtl.downgradeFromHlsDetailed` → `run`。
- 取源调用：`run` → `deps.prepare`（`PlayerAssembly.ets:214-218`）→ `StorePrepareExecutor.prepareDetailed`（`:58-67`）→ `submitToEngine`（`:98-104`）→ `engine.submit({kind:'Prepare'})` → `PlaybackCommandCenter.submit`。
- 结论：**降级 prepare 仍进入 `PlaybackCommandCenter.submit` 与 `CommandAdmissionCtl`**；它不是完全绕过 CommandCenter。它**不经过**的是用户 `Intent` → `PlayerInitLayer` 的正常 open/arm 流程。
- “第二道门禁”成立：`SourceDowngradeCtl.isCurrent/inFlight/tried` 位于 `engine.submit` 之前，先于 CommandCenter 判一次。它不能替代 CommandCenter 的 epoch/抢占/Release 槽。
- **口径差异（需确认）**：裁决文本称“绕开 CommandCenter 的 submit(Prepare)”；按 `StorePrepareExecutor.ets:104` 实际会调用 `engine.submit`。若“准入”指 UI/Intent 层，该表述成立；若指 CommandCenter，则与代码不符。§11 以代码事实为准，不按错误前提设计用例。

### 10.2 降级期间可能并发的用户命令

| 命令 | 路径 | 是否改变 gen/uri | 与降级的关系 | 已知风险 |
|---|---|---|---|---|
| **Seek** | `PlaybackControlFlow` → `PlaybackCommandCenter` `Seek` | 否（同 uri、同 gen） | `isCurrent` 仍为真，旧降级不会被它判 stale；Seek 可能与 `releaseBackend` / 新 prepare 交错 | Seek 可能落在旧后端（被释放）或新源 0 点；最终位置不保证（§11-DS） |
| **切歌** | `PlaybackEntryFlow`/`PreloadCommitFlow` → `Prepare`/`Adopt` | 是（uri 变则 gen+1） | 切走后 `isCurrent` 为假；旧降级在 release 后/prepare 后复检应 `Skipped` | 旧 `releaseBackend` 与新 open 的 prepare 可能争同一槽；epoch/抢占是否完全挡住需实测（§11-DC） |
| **Release** | `PlaybackLifecycleFlow` → `Release` | 是（`intent.reset()` → gen 0） | reset 后 `isCurrent` 为假；旧降级应 `Skipped`；`clear()` 只清 SourceDowngradeCtl 键 | reset 前窗口与 `releaseBackend` 可能竞态；`HlsDegradeCtl.inFlight` 只靠 finally 复位（§11-DR） |
| Play/Pause/SetRate | `PlaybackControlFlow` → CommandCenter | 否 | `isCurrent` 不覆盖；一般不影响取源，但可能落在旧后端 | 本轮不单独测，列观察项 |

### 10.3 isCurrent 复检覆盖结论

- `run` 三处复检：入口 `isCurrent(gen,uri)`；`releaseBackend` 后 `isCurrent(gen,uri)`；`serialPrepare` 后 `isCurrent(nextGen,uri)`（`SourceDowngradeCtl.ets:104,137,147`）。
- **切歌**：uri 变 → gen+1 → 后两处复检可挡住旧降级（时序上仍可能先 release 再切，见 §11-DC）。
- **Release**：`intent.reset()` → gen 0 → reset 后可挡住；reset 前窗口不覆盖。
- **Seek**：gen/uri 不变 → **不覆盖**；旧降级继续，Seek 是否生效取决于 CommandCenter 排队/新源，列为已知风险。
- **同 uri 原地重开（v1）**：gen 不变 → `isCurrent` **不覆盖**；v2 的 `uri#gen#attempt` + `latestKey` 才覆盖。本轮不测该场景（属 v2 准入），仅在 §10.2 登记。

### 10.4 已知风险登记（P0-1 关闭前需 §11 覆盖）

- **R1（Seek）**：`isCurrent` 不覆盖 Seek；降级期间 Seek 可能丢失或落到被释放后端。
- **R2（Release）**：reset 前窗口 + `releaseBackend` 直接释放，可能和 Lifecycle 的 release 竞态。
- **R3（切歌）**：gen 变化能挡旧降级，但旧 release 与新 prepare 的槽位竞争需实测。
- **R4（双门禁）**：降级 prepare 仍进 CommandCenter，`releaseBackend` 却在 CommandCenter 之外执行；两者之间无统一锁。

## 14 P0-1-WD 设计边界（播放中传输看门狗，不写代码）

### 14.1 目标与信号

- 目标：HLS 已出首帧后，传输半开/无数据导致位置停走时，在 N 秒内自动走既有降级链，而不是无限冻结。

### 14.2 不触发条件

- `Paused` / `Completed` / `Released` / `Error`：不触发。
- 应用后台 / 分屏失焦：不触发；回前台重新计时。
- `buffering=true`：不触发；缓冲结束重新计时。
- 非 HLS 源：不触发（SMB 自身失败走 §5）。
- 首帧未出：由现有 8s `PlayStallWatchdog` 负责，本 WD 不启动。

### 14.3 计时与宽限

- 看门狗只在首帧后 `Playing` 启动；tick 1s。
- **触发阈值 N = 12s**：连续 12s 位置不前进且视频帧率/渲染活性为 0。理由：SFF 段长 2s，12s = 6 段余量，能盖住抖动；小于 10s 易误杀，长于 15s 用户可感“卡死”。
- **Seek 宽限 3s**：收到 seek 请求/完成时重置 `lastProgress` 并进入 3s 宽限；宽限内不触发，宽限后重新累计 12s。
- 暂停/后台/缓冲：进入即重置 `lastProgress`，恢复后重新累计。
- 与 8s 首帧看门狗：8s 只在首帧前；首帧后立即 dispose，12s WD 才 arm；两者不叠加。若 8s 已触发降级，12s WD 不启动。

### 14.4 触发动作与门禁

- 触发只调用既有 `PlayerAssembly.failHlsStream('hls-playback-stall', -4, 'HLS 播放停滞')` → `HlsDegradeCtl.fail` → `SourceDowngradeCtl`；**不新增门禁、不直接调 `CommandCenter.submit`**。
- 单次：沿用 `HlsDegradeCtl.inFlight` + `SourceDowngradeCtl.tried`；同 `uri#gen` 只降一次。
- 不新增运行时兜底；异常路径仍归 `P0-1-F7`。

### 14.5 用户可感知上限

- 选定 N=12s；正常 SMB prepare ~0.3s，用户感知约 12–13s；最坏 prepare 5s 则约 17s。若要求严格 ≤15s，可改 10s（代价是 seek/抖动误判风险上升）。

## 17 P0-1 验收矩阵（两类素材，文档定义）

> 目的：把 P0-1 的“降级成功”拆成两类可判定验收，避免用不可解码素材证明降级链失败。
> 原则：素材代号化；每类按触发路径独立计数；n 为有效样本数，注入前已出首帧/已进降级的轮次不计。

### 17.1 可解码素材类（期望 DOWNGRADE_OK）

| 项 | 定义 |
|---|---|
| 素材 | `smb-decodable-sample-01`（H.264 1920×1080@30，SMB 直读可解）；`smb-decodable-sample-02`（H.264 3840×2160@30，用于 T2 小缓冲场景） |
| HLS 强制 | 夹具 `probe=transcode` 改写 `/probe.method`，使 SFF 走 HLS；`/vfs`、`/probe`、`/stream/start`、`index.m3u8` 均透传 |
| 样本量 | T1a / T1c / T2 各 **≥3** 次有效样本 |
| 判据（全部满足） | ① 目标 uri 恰好一次 `DOWNGRADE_OK`；② 新源 SMB `open path` 成功且代理持续 `served`；③ 无 `DOWNGRADE_FAIL`、无 `SOURCE_UNSUPPORTED`、无 Fatal/ErrorOverlay；④ 同 uri#gen 不再二次降级 |
| UI | 触发后无错误遮罩/错误文案（OCR 不含“错误/重试/不支持”）；允许 ≤1.5s 切换空窗，不单独判 fail |
| 失败条件 | 出现 `DOWNGRADE_FAIL`、Fatal、黑屏超 1.5s、二次降级、新源未取到数据 |

### 17.2 不可解码素材类（期望 DOWNGRADE_FAIL + 正确 Fatal）

| 项 | 定义 |
|---|---|
| 素材 | `undecodable-sample-01`（HEVC 2160×3840@60，v400 能力闸门判定超出设备） |
| 样本量 | T1a / T1c / T2 各 **≥3** 次有效样本（V402-041 阶段先到 2，剩余排队） |
| 判据（全部满足） | ① 目标 uri 恰好一次 `DOWNGRADE_FAIL`；② 紧随一次 Fatal + ErrorOverlay，文案可区分“素材不支持”与“网络异常”；③ 不自动重试、不循环降级；④ 不崩溃、不无限冻结 |
| 已知实现 | 降级 prepare 错误码 `-13` 由 V402-041 透传；Fatal 文案优先使用 `SOURCE_UNSUPPORTED_MESSAGE` |
| 失败条件 | 无 Fatal/无遮罩、Fatal 文案仍是纯网络错误、二次降级、崩溃 |

### 17.3 代号表

| 代号 | 类型 | 关键属性 | 用途 |
|---|---|---|---|

### 17.4 计数与关闭口径

- “有效样本”= 注入发生在 HLS 源已选定且（T1a/T1c）段请求已开始，或（T2）prepare 已 Ok 且首帧前。
- 可解码类三类全 ≥3 且 9/9 满足判据 → 降级链功能验收可关闭。
- 不可解码类三类全 ≥3 且 Fatal 文案正确 → 负路径验收可关闭；与可解码类互不替代。
- 任一类出现记 fail 的形态，P0-1 不关闭；样本不足写“待补”，不得用 n=1 冒充。
